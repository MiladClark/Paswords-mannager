# Security model — PassWards 0.3

This is an early implementation, not an independently audited password manager. Use test credentials until the design and implementation have received independent security review. The security boundary assumes the OS, application binary and bundled frontend are trusted while the vault is unlocked.

## Cryptography and storage

- RustCrypto Argon2id v1.3 derives a 32-byte key from the master passphrase, using a fresh 16-byte OS-random salt, 64 MiB of memory, three passes and one lane. Format 1 accepts only these fixed parameters, avoiding attacker-controlled excessive KDF costs.
- A separate OS-random 256-bit data key is wrapped using XChaCha20-Poly1305. The master passphrase and derived wrapping key are not persisted.
- Each record is encrypted and authenticated with XChaCha20-Poly1305 and a fresh 24-byte OS-random nonce. Associated data binds the format, vault identifier and record identifier. Record swaps between identifiers or vaults fail authentication.
- Record payloads include name, username, password, website, notes, folder, tags, favorite state, timestamps, custom fields and password history. SQLite contains only opaque identifiers, encrypted record blobs and a public key-wrapping header. File size, row count and ciphertext lengths remain observable. The header contains the salt, version, KDF parameters, vault identifier and wrapped key.
- SQLite runs with full synchronous commits and a rollback journal. Plaintext record values never enter SQL queries, logs, SQLite indexes or journal pages. Save operations commit before updating the in-memory index.
- Changing the master password verifies the current passphrase, generates a new data key and salt, re-encrypts every record and updates the header in a single transaction. A failure rolls back all records and the header; the in-memory key is changed only after commit. Copies of old backups remain decryptable with their old password; they cannot decrypt newly rotated vault ciphertext.
- Backup uses SQLite's consistent backup API and never writes a decrypted export. A backup import is authenticated in full first, then merged under fresh record IDs and the destination key in one transaction. Invalid or corrupt backups leave the destination unchanged.
- Keys, decrypted Rust JSON buffers and Rust record structures use `zeroize` on drop. List responses omit passwords, notes, custom values and password history; the selected record is decrypted on demand.

## Master-only authentication and legacy migration

The PIN feature and its native commands are removed. A locked vault opens only with the master password. Deletion and browser-fill approval verify that master again. Reading/editing inside an already unlocked vault needs no extra credential. Confirmation phrases prevent accidental deletion; they are not an independent authentication factor.

No PIN-wrapped vault key is written. After a verified master unlock, recognized legacy device-PIN files and interrupted PIN writes trigger full data-key rotation in the existing transaction-based rotation path. The old files are removed only after the new ciphertext/header commit. If cleanup fails, the current session is locked and the error is surfaced. Read-only backup imports do not perform device-file cleanup. Old snapshots necessarily retain their historical keys and credentials.

Five consecutive incorrect master checks begin a monotonic-clock cooldown, progressively 1–30 seconds, shared by verification actions for that vault in the running process. A successful check resets it. This is a UI/backend abuse limiter, not hardware protection: restart, local process tampering and offline attacks bypass it. A small offline common/repeated-password check applies to new passwords; it is not a comprehensive entropy estimator or breached-password database. Existing passwords are not silently rejected by stronger creation rules.

The live data key is held in an owned page-aligned allocation. On Windows, VirtualLock must succeed before a new session/key is committed. Drop zeroizes the full page before VirtualUnlock. This reduces pagefile exposure for that allocation only; derived keys, JS/IPC strings, cryptographic-library temporaries, screenshots, hibernation and crash dumps are not guaranteed to be scrubbed.

## Application boundaries

There is no trash command or soft-delete state. Permanent deletion checks an active master-password session, two exact copies of `I agree`, and a fresh master-password check in the same backend operation. Removing a record deletes its encrypted row and current-session metadata; it does not modify old backups or promise physical erasure. Legacy `deleted` fields are ignored during deserialization, keeping old records accessible without silently deleting them.

The bundled webview has no generic filesystem, clipboard or opener plugin permissions. Narrow Rust commands validate records, website schemes, sizes and session state. Only `http` and `https` websites can be opened; embedded URL credentials are rejected. File pickers run in Rust, so frontend callers cannot provide arbitrary backup paths. A backup export refuses to overwrite an existing file.

The production CSP blocks remote scripts, fonts, frames and connections. There are no remote icons, analytics, cloud APIs or embedded remote pages. Websites open only in the user's external browser after a user action. A single-instance plugin prevents competing PassWards instances. Window permissions permit dragging, minimize, maximize/restore and close for the integrated title bar. Browser integration adds narrow native commands; it does not give the webview a general IPC, registry or filesystem API.

## Browser extension boundary

The Manifest V3 extension connects through Native Messaging. The same PassWards executable runs a stdio-only native-host mode when invoked by the allowlisted extension origin, and forwards bounded messages to the running app. That mode never opens the database. A per-user named pipe rejects remote clients and uses an explicit DACL granting access only to the current user's SID. The first listener requires exclusive pipe ownership. Read/write timeouts, message-size limits, bounded concurrency and pipe-busy retries constrain resource use. The app exposes no localhost HTTP server.

Native host registration is scoped to HKCU for Chrome and Edge, with one fixed extension ID. This origin check is not protection from a local process running as the same user. The OS/user account and the installed extension package remain trusted. Publishing to an extension store may produce a different ID; that requires updating and reviewing the allowlist, not allowing arbitrary extension IDs.

Pairing is explicitly initiated in an unlocked desktop app using a six-digit, single-use code valid for two minutes and limited to ten attempts. A random 256-bit token is issued per connection. The desktop persists its SHA-256 digest inside a DPAPI-protected file. The extension stores its token only in `chrome.storage.local`, with access restricted to trusted extension contexts. It is not synced. Browser storage is not claimed to be a secure hardware keystore. Pairing tokens authorize origin-scoped metadata and fill requests; they do not authorize secret release without a new desktop approval. Each request carries a UUID; recent duplicates are rejected. Revoke in the desktop invalidates that token immediately and cancels its pending request.

Matching requires equal parsed scheme, hostname and port, excludes URL credentials, and excludes permanently deleted records. Metadata responses contain only ID, title and username, with at most 100 matches per request. A fill request binds one account, one origin, one paired client and a 90-second lifetime. The desktop shows the origin and account, then verifies the master password. Denial, lock, expiry or disconnection prevents release. The approved result is consumed exactly once; the backend rechecks item access, deletion and the stored URL before returning only username and password.

The background worker derives the origin from browser tab/sender APIs. It restricts content messages to frame 0, checks the active tab/document before requesting and before releasing, and targets the same browser document ID for insertion. Navigation invalidates a pending fill. The content script runs in the isolated extension world, rechecks `location.origin`, visibility, login-field heuristics and form destination, then dispatches native input/change events. It submits a form only when the user enables automatic sign-in, and rechecks the visible submit control, form validity, POST method, exact origin and target before submitting. For saving, it reads supported visible username/password fields after a trusted user edit and submission, or an explicit popup capture. Synthetic input/submit events do not trigger capture. Stored vault credentials are not returned to popup/content-message callers, captured passwords are never stored in extension storage or passed through DOM message events; the intended website can necessarily read credentials once they are filled.

The extension declares required HTTP/HTTPS host permissions and static top-frame content scripts for automatic login detection, with browser consent at install/update. Scripts run in the isolated extension world; no iframe is injected. Only a paired browser shows automatic suggestions. Automatic popup opening is limited to the active tab in a focused window and attempted once per document/URL; an inline picker is the fallback when the browser rejects opening the toolbar popup. Autofill excludes signup, hidden fields, OTP/PIN and cross-origin login frames. Capture can recognize matching new-password fields, but does not prove the server accepted a login or password change. The small in-page picker is page-visible UI, not a trustworthy OS surface; the desktop confirmation is the final approval surface.

Save candidates are tab/origin-bound, limited to 20 tabs and 120 seconds, and kept only in service-worker memory. A same-origin username-first step may retain a username for 120 seconds. Site permission removal, dismissal, tab closure or a different-origin navigation discards its candidate. Worker termination may lose unsaved candidates. Clicking Save or Update transfers a candidate to the local app, which keeps its password in a zeroizing buffer with a separate 120-second approval lifetime and periodic expiry cleanup. The desktop receives only metadata in its webview; its native backend independently verifies the master password, matching origin/username, selected account and previous-password digest before any write. Concurrent password edits cause a conflict instead of silent overwrite. Save replies carry status, never credentials. Lock/revocation clears pending native saves; denial also drops the transient password. JavaScript strings cannot guarantee physical memory zeroization.

Official API references: [Native Messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging), [Edge registration](https://learn.microsoft.com/en-us/microsoft-edge/extensions/developer-guide/native-messaging), [scripting targets](https://developer.chrome.com/docs/extensions/reference/api/scripting) and [extension storage](https://developer.chrome.com/docs/extensions/reference/api/storage).

The backend independently enforces a five-minute idle timeout and locks on minimization. A Win32 subclass registered for the current session locks the vault and clears pending browser requests/clipboard on session changes and suspend/resume notifications; it never unlocks it automatically. Failure to install this guard prevents app startup. The UI also clears its selected record, drafts, search index results and dialogs when it receives a lock event. Async responses from an earlier session cannot repopulate a locked UI. Native file pickers do not hold the vault mutex, so they cannot suspend timeout enforcement.

Copy operations are authorized again immediately before writing to the clipboard and serialized with vault locking. Windows receives an `ExcludeClipboardContentFromMonitorProcessing` hint. One backend worker expires the current clipboard lease after approximately 30 seconds, preserving values subsequently copied by another application and retrying when the clipboard is temporarily busy. Lock and exit also attempt to clear PassWards-owned content.

## Important limits

- Malware, administrators, debuggers, keyloggers, screen capture and a compromised webview or OS can access secrets while they are in use. This app cannot make a compromised computer trustworthy.
- JavaScript strings, IPC serialization, UI controls, OS clipboard memory, paging, hibernation and crash dumps cannot be guaranteed to be zeroized. Rust zeroization is best effort, not a claim that plaintext never exists in RAM.
- Third-party clipboard managers and remote-access software can ignore exclusion hints or capture values before cleanup. Abrupt process termination can prevent cleanup.
- Per-record AEAD detects changed ciphertext and record swaps. It does not prove database completeness or stop deletion, replay of older records, or rollback of the entire vault/backup. There is no trusted external monotonic state.
- Permanent deletion affects the current database only. Backups, filesystem snapshots, SSD wear leveling and external copies can retain previous ciphertext. Secure physical erasure is not promised.
- Browser-pairing DPAPI assumes the current Windows user and OS are trusted. No PIN is supported and there is no password-reset/recovery backdoor. Forgetting the master password can make data unrecoverable.
- Unlock and search are O(n) in record count, with decrypted search metadata held in Rust memory while open. There is no artificial record-count quota, and no infinite-capacity guarantee.
- Distribution is a standalone unsigned EXE, with installer bundling disabled and no updater or telemetry. The extension remains unpacked. Dependency-audit automation is a development/CI tool, never an app network dependency. Independent penetration/cryptographic review is still pending.

## Validation scope

Core tests use temporary directories and fictional secrets; they include a 10,000-record fixture, database persistence, ciphertext authentication, key rotation, transaction rollback under corruption, DPAPI browser-pairing persistence, master-only deletion, legacy-PIN key retirement, cooldowns, protected key allocation, backup retention/verification and Windows lock-event classification. Browser tests use only the development preview and fresh isolated browser contexts. Browser checks do not establish that the native OS clipboard, native file dialogs or integrated window controls work under every desktop configuration. The release is compiled separately; this version's native window controls still need an interactive check in the user's session. No real user vault is initialized or populated by automated tests.

## Verified local snapshots

Automatic snapshots are opt-in and default off. They contain the encrypted database only and are generated in a fixed app-data directory. Export reserves a new path without overwriting, uses SQLite backup, runs quick_check, compares the header and authenticates every record against the current session before reporting success. Failed outputs are removed. At most seven recognized regular snapshot files are pruned after successful backups; unrelated files and disabled backups are not deleted. The worker does not touch the idle timestamp. Local snapshots are not a replacement for an off-device backup and may retain permanently deleted records.

## Dependency review

JavaScript dependencies (including development dependencies) and the Rust lockfile were checked against package advisories during this change. No vulnerability entries were reported. The Rust lockfile also contains five warnings for proc-macro-error, zbus_names, zvariant, zvariant_derive and glib; these crates are absent from the Windows target dependency tree. They must be reviewed before enabling other desktop targets. CI reports advisories and blocks vulnerabilities or unsound dependencies in the Windows graph; it does not constitute an independent security audit.

Inline login menus show only metadata for the exact current origin. Filling still requires fresh desktop approval. Automatic sign-in is off by default; when explicitly enabled, the content script submits only a visible, valid POST form with a same-origin destination and no external target. Host access covers HTTP/HTTPS sites after the browser grants its required permission. There is no per-site detection toggle. Closing a suggestion does not repeatedly reopen it in the same document. Pairing is retained across browser/app restarts and vault locking; duplicate pairing calls reuse the stored token. Revocation is available only in the desktop app; a native browserUnpaired response clears the rejected local token. Removing the extension/profile or clearing its storage necessarily removes local pairing. Password generation is not exposed in the app or extension UI.

Site icons are read only from the browser favicon cache for the approved current origin; no favicon-provider service or arbitrary icon URL is fetched by the app. The extension normalizes the cached image to a 32px PNG. Native validation accepts bounded PNG data only (maximum 12,288 encoded characters; fixed 32px dimensions), and image bytes are inside each encrypted entry and its backup. The UI accepts only local PNG data URLs and falls back to initials on decoding failure. Changing an item to another origin clears its previous icon. The favicon permission is used only for the current saved site.

Manual Save prioritizes visible modal and focused-form fields instead of mixing unrelated forms on the page. Revealed passwords must retain a password semantic (autocomplete or a bounded password field name). Explicit capture can read visible read-only or temporarily disabled fields; autofill still excludes them. PIN/OTP names are matched as tokens, so site prefixes such as pinterest are not mistaken for PIN fields. Trusted login-button clicks can capture supported form-less login dialogs. Native origin/account validation and fresh master approval remain required. A stale content-script API is rejected with a page-refresh instruction before manual capture.

Save/update actions are rendered only in the extension popup; the website has no save card or floating save button. Automatic form submissions may request one popup opening per transient candidate, only for an active tab in a focused browser window and after verifying the candidate ID/origin. A blocked popup leaves the toolbar badge as the entry point. Manual capture does not request a second popup, and its button is omitted while a candidate already has a Save/Update action. Desktop master approval remains mandatory.
